# 异步初批的耗时测量

实际20次响应时间、P95、单次假模型耗时、队列长度、每任务最后一次消费耗时、attempts和死信数量，均在 [real-broker-result.json](async-grading/real-broker-result.json) 的metrics；运行时间、镜像ID和源码指纹在同一记录。

测量条件：本机Docker Desktop，真实RabbitMQ、SQLite共享目录、本地HTTP假模型（正常延迟200毫秒、崩溃案例2秒）。消费者停止时测20次提交，所有响应202且没有评分。P95使用20个样本按升序第19个（nearest rank）。

判据是提交P95小于单次假执行耗时，并结合“未启动消费者、模型调用不在HTTP请求中”的结构/场景证明异步。此数据不是吞吐容量评估；没有记录改造前真实供应商压测，不能编造“真实模型P95降低多少倍”。完整端到端完成时间也不能等同于最后一次模型执行耗时。

复现命令与清理范围见 [README](async-grading/README.md)。本次没有擅自设定生产并发量、费用或SLA；这些指标需要后续按实际部署单独确认。

## 三、索引改进（SQL 级 A/B）

同一 SQL、同一合成数据（50,000 分块，300 轮），只切换索引：

| 索引 | 执行计划 | 中位 (ms) | P95 (ms) |
| --- | --- | --- | --- |
| `(class_id, material_id)` | 回表 + 临时 B 树（LAST TERM OF ORDER BY） | 0.078 | 0.084 |
| `(class_id, material_id, chunk_index)` | **COVERING INDEX**，无临时排序 | 0.061 | 0.065 |

- P95 降低 **22.62%**，达到本课建议的“瓶颈档 P95 降 ≥10%”。
- **范围限制：这是 SQLite 查询级测量，不是 API P95**；不含应用层相似度计算、HTTP 与模型耗时。
- 变更提交：本次工作区未提交（`fe227a1` + dirty）。
- 迁移与回退：见 `migration/README.md`。

## 四、结论与未完成

1. 索引改进在 SQL 层有效，执行计划由回表 + 临时排序变为覆盖索引。
2. API 级前后复测未完成：检索接口受每日配额限制，接收接口会写库；需要账号池与独立数据快照后再测。
3. submit 的消费者执行吞吐未单独测；不能把 HTTP 接收吞吐当批改吞吐。
4. 历史 20 次异步耗时记录只能作基线，不能替代本课复测。
