## Context

已用独立 3009/8009 环境复现：教师停留 `view=subject-analysis&class_id=101`，另一页登录学生，再切 102 后显示 403。当前 Access Token 与完整身份只在各页内存；`cc_role`、`cc_has_token` 是浏览器共享且可改写的提示，无法代表发起导航的标签页会话。全部教师、学生、资料和根工作台页面已由 AuthGate 包裹，服务端业务数据始终经 JWT 接口读取。

## Goals / Non-Goals

Goals：合法任课切班保持原视图；业务子组件在身份恢复完成且角色匹配后才挂载；真实错误角色仍 403，刷新失败仍回登录。

Non-Goals：不提供持久的多账号独立刷新会话，不改后端权限、Cookie 属性/密钥、令牌寿命或身份数据；不修改先前命题作业功能。

## Decisions

1. middleware 保留为页面启动透传，不再读取辅助提示作拒绝决定。页面启动时只呈现加载占位，不向未知身份输出业务内容。单在切班前重写 Cookie 会产生标签页竞争，不能解决根因，因此不采用。
2. AuthGate 从当前内存会话或现有刷新接口恢复角色，先处理首次改密，再检查 `/teacher`、`/teacher/…` 与 `/student`、`/student/…`。路径正则必须含目录边界。角色匹配才设置就绪；渲染时也复核，防止原先 ready=true 导致角色变化时闪现业务子组件。
3. `route-access.ts` 只负责路径与角色匹配，不推断班级权限。实际任教/带班班级与学科检查仍由后端执行，不接受浏览器辅助 Cookie、URL 角色或伪造身份。
4. 离线回归执行真实 middleware 和 AuthGate（提供内存会话、路由及 React 调度替身），核验跳转和子组件是否挂载；浏览器重新走“双标签登录→单科切班”，补查资料、学生名单、作业、助手配置和真实错误角色访问。

## Risks / Trade-offs

- 页面 HTML 启动不直接按辅助 Cookie 拒绝 → 所有保护页面必须先渲染加载占位，未恢复/错误角色不得挂载业务子组件；接口仍强制认证，添加反向角色及伪造提示检查。
- 同一浏览器的刷新 Cookie 仍共享 → 当前有效内存会话可以继续操作；完整刷新后按服务端实际返回的身份重新校验，角色不符进入 403，不宣称持续多账号隔离。
- 一次错误路由可能已被浏览器缓存 → 构建新前端后重新加载页面并按实际服务验收。

## Migration Plan

无数据库迁移。保存旧前端镜像编号，全部门禁通过后仅重建本项目 frontend 并重启本套入口；后端、MCP、数据与其他 8080–8082 部署保持。异常时恢复旧前端镜像并重新创建该服务，无须恢复数据库。
