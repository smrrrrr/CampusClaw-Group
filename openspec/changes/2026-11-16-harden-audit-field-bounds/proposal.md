# 提案：审计日志字段转义与长度约束

## 背景

`security-fix-lesson09` 任务 4.6 要求：`write_audit_log` 对 `object_id` 等字段做 `json.dumps` 转义与长度截断，验证"提交带换行符的字段值后，日志行仍为一条完整 JSON"。

2026-11-16 逐条核对该变更时确认，这是 36 项未勾中**唯一实际缺失**的实现（其余 32 项已实现、3 项缺当次记录）。核对记录见 `reports/security-fix-lesson09-status-2026-11-16.md`。

## 现状与真实风险

`backend/services.py:78` 的 `write_audit_log` 把参数直接赋给 `AuditLog` 字段，没有任何清洗：

- **换行不构成日志破坏**：`backend/logging_setup.py:36` 的 `JsonFormatter` 用 `json.dumps` 输出，换行会被转义成 `\n`，日志行仍是单行。
- **真实风险是长度**：`models.py` 给 `action` 定了 `String(64)`、`object_id` `String(128)`、`skill_id` `String(64)`、`request_path` `String(256)`，但 SQLite 不强制长度，超长值会静默写入。一旦迁移到会校验长度的数据库，或按长度做索引/聚合，就会插入失败或截断行为不一致。
- **调用方各自截断，标准不统一**：`main.py:122` 手工写 `request_path[:256]`、`action=f"{method} {path}"[:64]`、`ids[-1][:128]`；`materials.py`、`student.py`、`lesson_plans.py` 的调用点则没有截断。新增调用点容易漏。
- **控制字符**：`\x00` 等控制字符进入数据库后，会让下游导出、比对、索引出错。

## 要做什么

在 `write_audit_log` 内部统一收口，调用方不再各自截断：

1. 字符串字段按模型列宽截断，超长部分丢弃并保留前 N 个字符；
2. 控制字符（除常规可打印字符外）替换为空格，避免破坏结构化导出；
3. 数值字段保持原样，`None` 保持 `None`；
4. 截断发生在入库前，**不改数据库列定义、不改调用方签名**。

## 不做什么

- 不改 `AuditLog` / `McpToolCall` 的表结构，不新增迁移；
- 不改任何调用方的传参方式（既有 `[:256]` 等手工截断可保留，属于冗余防御，不影响正确性）；
- 不记录正文、令牌、异常原文——这是既有约束，本次不加也不放松；
- 不引入新的依赖。

## 影响面

| 项 | 影响 |
| --- | --- |
| 行为变化 | 超长字段入库前被截断；含控制字符的字段被替换。正常长度的审计记录完全不变 |
| 接口 | 无变化，`write_audit_log` 签名不变 |
| 数据 | 无迁移，无历史数据回填；已有超长记录不受影响 |
| 门禁 | `make check` 新增一条离线回归，不影响 `make check-security` |

## 验收标准

- 提交含 `\n`、`\t`、`\x00` 的 `object_id` 后，落库值不含控制字符；
- 超过列宽的 `object_id`（如 500 字符）落库后被截断到 128 字符；
- 正常长度字段（如 `object_id="42"`）落库值不变；
- `None` 仍为 `None`，不被转成字符串 `"None"`；
- `make check` 通过。
