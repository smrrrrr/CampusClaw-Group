# 08 评审与完成定义规范 · CampusClaw

适用：全部变更。完成定义与门禁常驻 `AGENTS.md` / `CLAUDE.md`，每次会话都会读到。
被谁读到：`AGENTS.md`；技能 `review-change`。

## 1. 完成定义（Definition of Done）

一条变更同时满足下列五条才算完成：

1. 规约中的每个 Scenario 都有对应检查，越权与失败路径也有；
2. `make check` 全部 PASS；
3. 涉及提示词改动时，评测或抽查记录已归档（06-AI应用规范 §7）；
4. 文档同步：README（功能、版本记录）、主规约、`docs/standards/` 中受影响的条目、`models.py` 注释；
5. 验证记录写进变更目录的 `validation.md` 或 `docs/`，能按变更名找到。

判据：逐条打勾，勾不上的那条就是没做完的部分。“模型说完成了”不等于完成。

## 2. 变更规模上限

一次变更不超过 `tasks.md` 中的一组任务的实现量；一次提交只含一组任务。超出就拆成多次变更或多次提交。

## 3. 评审检查表

| 谁来审 | 看什么 |
| --- | --- |
| 人（另一名组员） | 规约覆盖：场景是否真的满足；授权：越权是否被拒、身份是否只取自会话；数据：迁移是否可重跑、是否先备份；提示词改动是否评测 |
| Harness（技能 `review-change`） | 规范一致性：分层、接口命名、错误响应、日志字段、重复代码、测试三类是否齐 |
| 工具（`make check`） | 规约格式、分层、密钥、类型、回归；不占人工评审时间 |

## 4. 责任人与时限

每次变更指定一名评审人；评审请求一个工作日内响应。超期由提出者在组内群里升级，不自行合入 `main`。

## 5. 门禁必跑

合并到 `main` 前必须本地执行 `make check` 并全部 PASS，把结果尾部贴进 PR 说明。不得为了变绿而放宽检查、删除断言或跳过子项。

## 6. 例外书面化

确有理由保留不符合规范的写法时，把例外写进对应规范文件，写明“例外（书面）/ 理由 / 失效条件”（示例：02 后端规范的 `/api/v1` 前缀、03 安全规范的跨班 403）。只在会话或群聊里口头同意的豁免无效。

## 7. 证据归档与提交信息

- 变更目录：`openspec/changes/YYYY-MM-DD-<短横小写英文名>/`，验收后归档到 `openspec/changes/archive/`。
- 提交信息第一行写“改了什么”，正文末尾三行写依据，值必须查得到：

```
feat(health): /api/health 返回版本、时间与依赖状态

Change: 2026-10-28-engineering-baseline
Verify: make check
Evidence: docs/lesson-07/verification.md
```

不写 `update`、`fix` 这类无信息的提交信息。

## 8. 改这些文件要人审

`AGENTS.md`、`CLAUDE.md`、`.claude/`、`.trae/`、`docs/standards/`、`openspec/`、`scripts/`、`Makefile`、`docker-compose.yml`、`deploy/`。改动要在变更说明里写清改了什么、为什么、怎么验证；Harness 不得自行放宽其中的检查。

## 违反时

先判定是“流程没走”还是“判据不清”：前者退回补流程，后者改本文件并写进变更说明。
