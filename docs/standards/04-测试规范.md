# 04 测试规范

**什么时候读：** 改 `apitest/**`、检查脚本，或实现一组任务后。由AGENTS与`add-tests`引用。

**这份规范要保证：** 检查能发现错误，而不只是证明程序跑过。任何检查失败都阻断合并，不能删断言、跳过子项或放宽标准。

## 1. 检查放在哪里

| 类型 | 文件位置 | 怎样运行 |
| --- | --- | --- |
| 接口/业务回归 | `apitest/check_<能力>.py`；临时SQLite、TestClient、假模型 | make check |
| 前端可独立验证的逻辑 | `apitest/check_<模块>.cjs` | make check |
| 运行中服务的在线接口 | `apitest/cases/api/...` | 启动后运行 `python apitest/run_all.py`，不在门禁内 |
| 真实模型探针 | `apitest/probe_*.py` | 手动运行，结果存docs/eval |
| 页面实际操作 | 浏览器验收记录 | 按角色、范围、四态和关键流程逐项操作 |

门禁自动收集check_*.py和check_*.cjs。新业务能力新增/扩展对应检查；纯文档整理记录结构、链接、适用性，不虚构接口。

## 2. 每条检查都能说清在验哪条要求

检查名直接使用Scenario标题，或采用“R编号 正常/失败/边界：场景要点”。

一条验收至少写清：

1. **前置：** 账号、角色、班级、状态、数据与依赖。
2. **操作：** 发什么请求或点击什么。
3. **结果：** 状态码、可见内容、数据库及文件应怎样变化。

对应表使用 `能力/Scenario → 检查文件和检查名 → 本次结果 → 证据路径`。只写“有测试”不够。

## 3. 正常、失败、边界都要测

| 分组 | 最少考虑什么 |
| --- | --- |
| 正常 | 合法角色、合法状态和有效数据下完成业务 |
| 失败 | 参数非法、未登录、无权限、资源不存在、依赖不可达 |
| 边界 | 长度/数量/时间/阈值两端、空集合、最后一页之后 |

越权成对出现：未登录与他人账号访问。涉及班级/学科时补对应跨范围案例。用明确等价类和边界值，不用随机值代替设计。

## 4. 断言业务结果，不只断言形状

下面两条不能单独作为验收：

```python
check('返回成功', response.status_code == 200)
check('有数据', len(response.json()) > 0)
```

还要检查具体值：有没有对方资料、发布后恰好几条记录、失败后是否保持原数据、是否留下新文件、日志有没有令牌。

**有效性验证：** 新增检查时至少故意改坏一处关键逻辑，确认对应检查变红，然后恢复正确实现再跑。把改坏点、失败检查名、恢复后结果写入validation。

## 5. 数据和外部依赖必须隔离

- 临时库和上传目录放TemporaryDirectory，导入main前设置DATABASE_URL/UPLOAD_DIR。
- 不读写真实data/current，不运行dev_seed重置现有账号。
- 每个脚本自建班级、教师、学生，不依赖执行顺序。
- 模型、MCP、网络均用替身。门禁使用专用测试JWT、空模型Key和不可达地址，不耗真实模型额度。
- 在线用例只使用演示数据；必要写入用uuid命名并在末尾清理。

**检查目标：** 断网时离线回归结果不变；故障注入只能影响临时环境。

## 6. 失败怎样判定

本项目按HTTP、响应字段、数据/文件变化和页面表现判断，没有独立错误码系统。

| 结果 | 本项目的判据 |
| --- | --- |
| 成功 | 2xx，且完成预期数据变化、无越权内容 |
| 参数非法 | 400/422 |
| 未登录 | 401 |
| 无权限 | 403；私有资源隐藏规则以主规约为准 |
| 不存在 / 冲突 / 依赖不可用 | 404 / 409 / 503 |
| 被当成成功 | 负例拿到2xx，或产生约定外变化/内容 |
| 被放行 | 得到无权数据或越权写入生效 |
| 被误拒 | 合法操作没有成功或缺少预期副作用 |
| 未处理故障 | 500、泄露堆栈/内部异常，或只有无信息的错误提示 |

SSE检查error/done事件及是否落库；不能把模型失败当空结果成功。日志、附件和审计也要检查，不只检查响应码。

## 7. 一键门禁

从仓库根目录运行：

```text
Windows:      backend/.venv/Scripts/python.exe scripts/check.py
macOS/Linux:  make check
```

也可使用对应venv Python执行scripts/check.py。门禁包含OpenSpec、分层、密钥、前端类型及全部离线回归；任一子项非零就不通过。

## 8. 改完代码后怎样验证

1. 修缺陷先加复现检查，确认旧实现失败。
2. 修实现，保留该检查，再跑所需回归和完整门禁。
3. 如果断言本身有错，先核对规约，说明修改理由，不能自行删除或放宽。
4. 规范和用例冲突时按变更流程澄清，不能选择性跳过。

## 9. 验证记录要区分什么

记录本次时间、命令、环境、提交/工作区状态、数量和退出码。历史结果只引用，不改日期冒充复跑。

自动检查、浏览器、真实模型、另一名组员评审分别记录。缺凭证、外网、人工或执行器的项标为待验；静态数据准备不等于模型评测通过。没有对应检查的条目标为“未覆盖”，不能因其他测试全绿而宣称符合。

## 违反时

任一检查失败都阻断合并。保留复现、实际结果和证据，按规约修复后复跑；规范与用例冲突先澄清，不能自行跳过或放宽断言。
