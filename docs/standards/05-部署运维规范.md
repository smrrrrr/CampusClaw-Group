# 05 部署运维规范 · CampusClaw

适用：`backend/Dockerfile`、`frontend/Dockerfile`、`mcp-server/Dockerfile`、`docker-compose.yml`、`deploy/`、`.env.example`。
被谁读到：`AGENTS.md` 规范索引（改上述文件时必读）；技能 `release`、`fresh-start`。

## 1. 可复现构建

- 依赖锁文件入库并按锁安装：后端 `uv.lock`（`uv sync --locked --no-dev`），前端 `package-lock.json`，MCP 服务 `uv.lock`。
- 镜像只装运行所需；不在镜像里放 `.env`、数据库、上传文件（各目录 `.dockerignore` 已排除）。
- 版本号写在 `backend/version.py`，与 Git 标签一致（`v1.2.0` ↔ `APP_VERSION = "1.2.0"`）。

**例外（书面）**：`backend/Dockerfile` 用 `ghcr.io/astral-sh/uv:latest` 拷贝 uv，基础镜像用 `python:3.12-slim` 浮动标签，同一提交两次构建不保证逐字节一致。失效条件：第一次因上游镜像变化导致构建差异时改为固定版本。

## 2. 环境与配置

| 环境 | 怎么起 | 数据 |
| --- | --- | --- |
| 开发 | 本机 `docker compose up -d --build`，或后端 `uvicorn` + 前端 `npm run dev` | `data/current/`（组内数据包恢复） |
| 测试 | `make check`（临时库） | 每次新建，用完即删 |
| 演示 / 部署 | 同一份 Compose，换 `.env` | 部署机自己的 `CAMPUSCLAW_DATA_DIR` |

同一镜像跨环境，只换 `.env`。对外入口只有 Nginx（`CAMPUSCLAW_PORT`，默认 8080）；backend、frontend、mcp-tools 只在 Compose 内网 `expose`，不映射宿主端口。

## 3. 健康检查

- `GET /health`（Nginx 别名）与 `GET /api/health` 免认证，返回 `status`、`version`、`time`、`dependencies{database, mcp_tools, model}`；数据库不可读返回 503；MCP 不可达返回 200 + `degraded`。只返回状态枚举，不返回地址、键名、异常原文。
- Compose 的 backend 健康探针调用 `/api/health`；nginx 与 frontend 依赖 backend `service_healthy` 才启动。
- 每次部署和每课验收都从 `curl -s http://localhost:<端口>/health` 开始。

## 4. 结构化日志

后端每行一条 JSON，字段：

```json
{"ts":"2026-10-28T02:00:00.123Z","level":"info","module":"access","request_id":"4f3c…","method":"GET","path":"/api/health","status":200,"duration_ms":3.1}
{"ts":"2026-10-28T02:00:01.456Z","level":"info","module":"lesson_service","request_id":"4f3c…","msg":"学生稿 LaTeX 反斜杠修补 2 处"}
```

- 每个响应带 `X-Request-ID` 头；调用方传入合法的 `X-Request-ID`（8–64 位字母数字 `._-`）时沿用，否则服务端生成。
- 不得记录：查询串、`Authorization`、Cookie、口令、令牌、`.env` 密钥值、学生提问原文、资料正文。
- 查看：`docker compose logs backend | grep '"request_id":"<id>"'` 串起同一请求。

**现状（书面）**：`mcp-server/` 与前端仍是文本日志；指标与告警未接入。后续课次接指标时沿用以上字段。

## 5. 发布与回滚

发布按技能 `release` 执行，顺序：

1. `make check` 全绿；
2. 备份数据库（见 §7）；
3. 改 `backend/version.py` 与 README 版本记录，提交；
4. `docker compose up -d --build`，等 backend 健康；
5. `curl /health` 确认 `version` 为新版本、`status` 为 `ok`；
6. 打标签 `vX.Y.Z` 并推送，在 `docs/releases/YYYY-MM-DD-vX.Y.Z.md` 记录版本、包含的变更、验证结论。

回滚只有一条路：`git checkout <上一个版本标签>` → `docker compose up -d --build` → 如有数据结构变化，恢复发布前备份。回滚路径每个迭代至少演练一次并记录耗时；未演练过的回滚不算可用。

## 6. 数据变更顺序

加字段 → 新代码兼容读写 → 发布 → 确认后再删旧字段。删除类操作放在最后，且旧版本代码在新结构上仍可运行（保证回滚可用）。迁移细则见 07-数据规范。

## 7. 备份与恢复

- 停写后备份：`docker compose stop backend`，复制 `${CAMPUSCLAW_DATA_DIR}/campusclaw.db` 为 `before-<动作>-<时间>.db`，与 `backend/uploads/` 一起保存；或用 SQLite backup API 在线备份。
- 目标：RPO ≤ 1 天（每天课后备份一次），RTO ≤ 30 分钟。保留最近 7 份。
- 每学期做一次恢复演练（用组内数据包恢复脚本恢复到新目录并跑 `/health`），记录用时。未演练过的备份不作为恢复依据。

## 8. 性能与限流

- MCP 每题 / 每会话调用上限、模型调用超时在 `config.py` 集中配置；学生每日提问上限 `AI_DAILY_LIMIT` 是代码常量（随版本变）。改动都走变更。
- 网关额度：每人每日 10 万 token；批量生成前先查剩余额度。

## 违反时

涉及健康检查、回滚能力或数据目录的改动需另一名组员复核，并先在本机演练一次再用于演示环境。
