# 05 部署运维规范

**什么时候读：** 改Dockerfile、Compose、deploy、环境模板，或部署/发版时。由AGENTS、`release`和`fresh-start`引用。

**这份规范要保证：** 别人能按文档启动，服务异常能判断，更新失败能恢复数据和旧版本。

先记住：按锁构建；配置外置；先备份再变更；没演练过不能写“回滚可用”。

## 1. 可复现构建

- 后端/MCP提交uv.lock，按 `uv sync --locked --no-dev` 安装；前端提交package-lock.json并按锁安装。
- 镜像只装运行所需；不包含.env、数据库或上传目录，检查各目录.dockerignore。
- 正式版本写在backend/version.py，并与发布标签对应。工作区临时更新不冒充正式版本发布。

**书面例外：** 当前从 `ghcr.io/astral-sh/uv:latest` 取uv，Python基础镜像用 `python:3.12-slim` 浮动标签，不保证两次构建逐字节一致。若首次因上游变化发生构建差异，改为固定版本；不能把“有锁文件”当作镜像完全可复现的证据。

## 2. 环境与配置

| 环境 | 启动方式 | 数据 |
| --- | --- | --- |
| 开发 | Compose或本机uvicorn + npm run dev | 本机自己的目录；已有数据不重置 |
| 测试 | make check | 每次新建临时库与上传目录 |
| 演示/部署 | 同一Compose，使用各自.env | 各部署自己的CAMPUSCLAW_DATA_DIR |

相同镜像跨环境使用，不硬编码真实地址和密钥。只由Nginx暴露CAMPUSCLAW_PORT；backend/frontend/mcp-tools仅在Compose内网expose。

作业初批增加RabbitMQ、grading-dispatcher与grading-worker。代理仅内网可达、数据卷持久化；就绪检查以rabbitmq用户运行，避免root探针抢先生成不可读的内部cookie。队列密码只在.env。任务已存数据库但代理暂不可达时可202接收，页面保持排队，投递器恢复后补投。已获确认的pending消息不再周期补投；正常停启依赖持久消息和卷。仅管理员明确清空代理数据后，在停消费者的前提下用grading_worker.py --recover-pending恢复待投递标记；正常暂停不能运行该命令。旧GRADING_REPUBLISH_SECONDS不再生效。主health不代表消费者存活；队列长度、attempts、死信及停启检查见根reports/async-grading。

关键JWT配置缺失要启动失败。可选模型/MCP有明确未配置/降级状态，不能把应用启动成功当作这些能力已可用；详见02规范第7、9节。

## 3. 健康检查

`/health`由Nginx转发到免认证的`/api/health`。每次部署、课程验收先读取它。

| 情况 | 预期结果 |
| --- | --- |
| 依赖正常 | status=ok，含version/time/dependencies |
| 数据库不可读 | HTTP 503 |
| MCP不可达 | HTTP 200，status=degraded |
| 可选模型未配置 | dependencies.model=not_configured |

只返回状态，不回显地址、密钥键名或异常原文。Compose后端探针调用/api/health，入口与前端依赖后端健康后启动。

**检查：** `curl -s http://localhost:<实际端口>/health`，或PowerShell的Invoke-RestMethod。实际端口看本次.env，不假设一定是8081/8083。

## 4. 结构化日志

后端每行是一条JSON；访问日志至少包括：

| 字段 | 含义 |
| --- | --- |
| ts / level / module | 时间、级别、模块 |
| request_id | 本次请求标识 |
| method / path / status | 请求方法、无查询串路径、状态码 |
| duration_ms | 耗时 |

业务日志使用同一request_id及msg。调用方标识为8–64位字母数字或`._-`时沿用，否则生成；响应头带X-Request-ID。

不得记录查询串、Authorization、Cookie、口令、令牌、密钥、学生提问原文或资料正文。

**检查：** `apitest/check_baseline.py` 的R2组核对逐行JSON与标识；按request_id串起访问和业务日志。

查看日志用 `docker compose logs backend`，再按指定request_id过滤；Windows可用Select-String，其他环境可用grep。过滤时不把令牌或密钥当检索文本。

**当前差距：** 前端/MCP仍有文本日志，指标告警未接入。不能宣称全项目日志已统一。

## 5. 正式发布与回滚

正式发布按release技能执行，顺序不能颠倒：

1. 完整make check通过。
2. 备份数据库和匹配的上传文件。
3. 更新版本及README记录，按授权提交。
4. 构建并启动，等待健康。
5. 核对health中的版本、状态与预期依赖。
6. 在授权后打标签、推送，写docs/releases中的发布记录。

回滚使用已记录的旧镜像ID，或已确认标签对应的源码重建；不能覆盖未保存的工作区。涉及数据/文件时，先保存更新后的新数据，再恢复匹配备份。

**检查目标：** 每个迭代至少演练一次回滚并记录耗时。未演练的方案只写“待验”。

## 6. 数据变更顺序

新增字段→兼容读写→发布→确认→另起变更删除旧字段。删除操作放在最后，旧版本对新结构的兼容性要验证；细则见07规范。

## 7. 备份与恢复

备份可停写后复制数据库，也可用SQLite backup API；都要同时保存匹配的backend/uploads。已有数据的库不运行dev_seed。

| 目标 | 怎么证明 |
| --- | --- |
| RPO≤1天 | 实际备份时间间隔不超过1天 |
| RTO≤30分钟 | 在新目录恢复到health可用的实测耗时 |
| 至少保留最近7份 | 清点实际备份，不自动推断已执行 |

当前没有自动备份/清理。删除备份按07规范处理，不因“保留7份”擅自删掉旧包。每学期至少做一次新目录恢复演练；没有演练记录的备份，不当作已验证恢复依据。

恢复后检查integrity_check=ok、关键表行数、文件SHA-256及health。不能把旧库与不匹配的新文件混用。

## 8. 性能、超时与额度

- MCP每题/会话上限和模型超时由config集中定义。
- 学生日提问上限AI_DAILY_LIMIT属于随版本变化的代码常量；修改走变更。
- 课程网关额度按课程账号约定（每人每日10万token），批量调用前查剩余量；本机其他供应商不套用该额度数字。

## 9. 停机演练与证据

仅在独立演示目录注入故障，不操作真实教学库：发起可识别的测试读写，再正常停止服务，例如 `docker compose stop -t 30 backend`。

检查已提交数据可读、未提交操作没有半成品、服务可再次启动。30秒是演练目标，不是既有实测结论。

记录开始/结束时间、退出码、信号、数据完整性与重启health。涉及健康、回滚或数据目录的变更，要由另一名组员复核并先演练；当前机器自检不能代替另一人的结论。

## 违反时

健康、备份或恢复结果不符合本次发布要求时，记录失败并停止推进发布；按已记录的方案恢复。涉及健康检查、回滚或数据目录的改动，补齐另一名组员复核和隔离演练。
