# 待讨论：还需要保证哪些事

**状态：讨论稿。** 本页梳理如何验证AI完成的代码任务，不修改当前功能、业务规约或检查程序。下列新增建议需要讨论确认后，再写入正式条款和对应检查。

已有的权限、数据保护、不得放宽门禁等要求继续有效，不因本页标为讨论稿而变成可选项。

## 1. 先明确我们要验证的两件事

- **功能符合规约：** 该完成的结果发生了，不该发生的副作用没有发生。
- **实现符合规范：** 分层、权限、数据、错误、日志及验证过程符合工程约束。

代码能运行、AI说已完成、部分测试全绿，都不能单独证明上面两点。

## 2. 优先讨论的五项

| 建议 | 要防止的问题 | 可以怎样验 | 需要先决定什么 |
| --- | --- | --- | --- |
| 任务边界明确 | AI顺手改了无关功能、依赖、配置或数据 | 任务开始列允许改动范围；交付时对照实际diff和副作用 | 哪些文件必须单独审批，哪些属于合理联动修改 |
| 验收标准不能自行改低 | 修代码失败后改断言、快照或规则，让结果变绿 | 对比任务前后的规约、检查、忽略项；标准变化单独列出理由和复核 | 由谁确认标准变化，如何和正常测试维护区分 |
| 预期结果有独立依据 | 实现和测试出自同一次错误理解，互相印证 | 从Scenario写固定输入和预期；不能只调用生产函数算“标准答案”；关键结果另核对 | 哪些场景保留独立反例/固定样例，由谁复核 |
| 原有功能有基线 | 新功能通过，却破坏旧流程、旧数据或接口 | 记录受影响的现有流程及数据；比较修改前后行为，跑对应回归 | 基线覆盖哪些流程，兼容性变化怎样声明 |
| 每个要求都有明确状态 | 把“没测”藏在“整体PASS”里 | 按条款列已验证/失败/未覆盖/不适用及理由；结果绑定本次代码、命令与证据 | 是否把未覆盖的关键项作为提交或合并阻断项 |

这五项中，测试不可放宽、回归和证据真实性已有规范基础；待补的是覆盖清单、独立复核和可追踪的执行方式，不是重新批准这些基本要求。

## 3. 项目里已有要求，但需要补齐覆盖的地方

| 已有要求 | 现有基础 | 还需要核对什么 |
| --- | --- | --- |
| 权限按资源判断 | 安全规范、班级/学科/附件检查 | 是否每个相关读写接口都有未登录、他人、他班、他科和错误角色案例 |
| 并发与重试不损坏数据 | 事务、幂等、评分竞态检查 | 重复点击、网络重试、旧版本写回和部分失败，是否覆盖本次改动涉及的路径 |
| 失败是完整失败 | HTTP/SSE、整批回滚和文件清理 | 有没有错误被吞掉、返回成功但未完成、或遗留半成品的路径 |
| 页面范围和状态正确 | 页面四态、切班回包、AuthGate检查 | 多标签页、刷新、退出、过期、切班的组合是否实际操作过 |
| AI输出不能充当事实证明 | 固定用例、引用规则、提示词版本要求 | 20条数据的真实执行器、案例级结果、模型变更前后比较仍待完成 |
| 构建、恢复可以复现 | 锁文件、health、备份及回滚流程 | 新机器、新会话、故障和恢复耗时有没有真实证据 |

不能把“存在一个检查脚本”写成“同类要求全部覆盖”。应先做条款到检查的映射，再决定补什么。

## 4. 不能在本轮擅自决定的边界

- **多账号会话：** 当前修复保证有效会话不被共享辅助角色提示误拒；是否需要跨标签页、跨部署长期独立保存多个账号，是新的产品/会话设计问题。
- **性能与成本：** 若要要求响应时延、并发量、模型耗时或调用费用，先明确测量环境与阈值；不自行编造一个数字并声称当前满足。
- **自动判定范围：** 分层、类型和部分结构可自动检查；业务语义、页面体验、真实AI回答及另一人独立复现，仍需相应的集成、浏览器、评测或人工证据。
- **历史缺陷：** 现有规范目标与旧实现的差距要保留；不能为了本次“全绿”改低要求，也不能未经讨论扩大成全项目重构。

## 5. 下次讨论可以直接回答的问题

1. 先选哪个真实AI代码任务做验收样例？
2. 哪些条款必须自动阻断，哪些允许人工复核？
3. 哪些关键预期需要独立样例或另一人复核？
4. 有未覆盖项时，允许交付到什么阶段？
5. 验收标准本身发生变化，由谁确认？

确认后再决定新增检查器、测试和门禁；本轮先把文档读清楚，不实施这些建议。
